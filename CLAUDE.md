## What we are building

**Working name: Fretkey** (rename freely). A subscription web app that teaches music theory from basics to advanced, *on the instrument*: guitar and piano. Every lesson follows the same four steps:

1. **Understand** – a short, plain-language explanation
2. **Listen** – hear the concept (played samples, no reading required)
3. **Learn** – see it on an interactive fretboard or keyboard
4. **Practice** – drills on screen, then play along on a real instrument

Target user: a self-taught player who knows shapes and songs but not why they work. The owner has 7–8 years of guitar experience and is the quality bar: nothing ships that would feel shallow or wrong to an experienced player.

Web first (responsive + installable PWA). Android and iOS apps come later and will reuse the same API and the `src/core` code.

## Stack (do not substitute without asking)

- **Next.js 16**, App Router, TypeScript strict, Turbopack. Run `npm show next version` and use the latest stable 16.x.
- **API: Next.js Route Handlers only**, under `src/app/api/v1/`. No Express, no separate server, no tRPC.
- **MongoDB Atlas + Mongoose.** One cached connection helper in `src/server/db/connect.ts`.
- **Auth: Better Auth** with `@better-auth/mongo-adapter` (email + Google). Chosen because it also has an Expo plugin for the later mobile apps.
- **Payments: Razorpay Subscriptions** (UPI Autopay + cards). Webhooks are the source of truth for subscription state.
- **Validation: Zod** on every API input and on all lesson content.
- **UI: Tailwind CSS + shadcn/ui + Motion** for animation. Icons: lucide-react.
- **Client data: TanStack Query.** Server Components for read-only pages.
- **Music: `tonal`** for theory maths, **Tone.js** for audio playback with real instrument samples, **VexFlow** for staff notation (lazy-loaded, only where needed).
- **Tests: Vitest** (unit, especially `src/core`), **Playwright** (key flows).

Library APIs change. Before using a library feature you are not certain about, check its current docs instead of relying on memory.

## Architecture rules

1. **`src/core` stays pure.** It will be shared with the mobile apps. If a file there needs React, the DOM or the database, it belongs elsewhere.
2. **Route handlers are thin:** parse with Zod → check session/entitlement → call a service → return JSON. No business logic or Mongoose queries inside handlers.
3. **One response shape:** `{ data }` on success, `{ error: { code, message } }` on failure, with correct HTTP status.
4. **Mobile-ready API:** every feature the web UI uses must be reachable through `/api/v1`. Do not hide core logic in Server Actions.
5. **Entitlements are enforced on the server.** Paid lesson content is never sent to a non-subscriber; hiding it in the UI is not enough.
6. **Subscription state changes only from verified Razorpay webhooks** (verify the signature, make handlers idempotent). Never trust the client's "payment succeeded".
7. **Theory is instrument-agnostic; instruments are views.** A lesson defines notes/intervals/chords once. `Fretboard` and `Keyboard` render the same data. Never hard-code guitar-only logic into lesson content unless the block is explicitly instrument-specific (e.g. CAGED).
8. **Content lives in `content/` as typed files**, validated by Zod in `npm run seed`. Do not hand-edit lesson documents in the database.
9. **Audio starts only after a user gesture.** Lazy-load Tone.js and samples; never block first paint on audio.
10. Secrets only in `.env.local`; keep `.env.example` updated. Never commit keys.

## Music correctness (non-negotiable)

- Spell notes correctly for the key: F# major has E#, not F. Use `tonal` and the helpers in `src/core/theory`; never build note names by string hacks.
- Guitar default is standard tuning E2 A2 D3 G3 B3 E4, but tuning is a parameter, never a constant buried in a component.
- Support left-handed fretboard and both note-name systems where shown (C D E… and optional Sa Re Ga / Do Re Mi later).
- Every function in `src/core/theory` and `src/core/instruments` needs unit tests with real musical cases.
- Formulas for intervals, scales and chords must match the reference tables in `docs/CURRICULUM.md`; write tests that assert them.
- The Theory Canvas has one state object driving fretboard, keyboard and theory panel (see `docs/CANVAS.md`). Never give an instrument component its own copy of musical state.
- Note markers use only the three visual roles defined in `docs/CANVAS.md` (root, chord tone, scale note). Do not invent extra colours.
- If unsure whether a theory statement is right, say so and flag it for the owner's review instead of guessing.

## Product and UX rules

- A lesson takes 5–8 minutes. One idea per lesson. Short sentences, no jargon before it is taught.
- Always let the user **hear** something within the first 30 seconds of a lesson.
- The instrument toggle (Guitar / Piano) is always visible in a lesson and remembers the user's choice.
- Mobile-first layouts. The fretboard must be usable on a 360px-wide phone (horizontal scroll with snap, large touch targets ≥ 44px).
- Instant feedback on every drill answer: sound + colour + one-line reason why.
- Never dead-end a user: every screen has one clear next action.

## Design system: premium feel

- Dark theme first (light theme supported). Deep neutral background, one warm accent (amber/gold), one success and one error colour. No rainbow UI.
- Generous spacing, large confident typography: a display serif for headings, a clean sans for body. Load via `next/font`.
- Fretboard and keyboard are the hero visuals: crisp SVG, subtle wood/ivory texture hints, glowing note markers, smooth 150–250ms transitions.
- Motion is purposeful: step transitions, note pulses, streak celebrations. Respect `prefers-reduced-motion`.
- Use design tokens (CSS variables in `globals.css` mapped into Tailwind). No one-off hex colours or magic spacing in components.
- Skeletons instead of spinners. No layout shift. Target Lighthouse performance ≥ 90 on mobile.
- Accessibility: keyboard navigable, visible focus, colour is never the only signal, contrast ≥ WCAG AA.

## How to work

- Work on **one task from the current phase** in `docs/BLUEPRINT.md` at a time. State the plan briefly, then implement.
- Keep changes small and focused; do not refactor unrelated code.
- Add or update tests with every change to `src/core` or `src/server/services`.
- When a phase task is finished, tick it in `docs/BLUEPRINT.md`.
- Ask before: adding a dependency not listed above, changing the data model, or changing a public API contract.
- Prefer the simplest solution that meets the blueprint. No speculative abstractions.

## Do not

- Do not add Express, a separate backend, Redux, or a second database.
- Do not build microphone pitch detection, MIDI input, or native apps before the blueprint phase that introduces them.
- Do not write placeholder lesson content that states music theory you have not verified.
- Do not store card or UPI details; Razorpay holds them.
- Do not add copyrighted songs, tabs, lyrics or recordings to `content/`. Use original study pieces and public-domain tunes only.
- Do not invent technique instructions (fingering, picking direction, hand position); mark anything unverified for the owner's review.
